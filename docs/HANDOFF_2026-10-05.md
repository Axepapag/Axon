## 2. The 16D / 1024D question, in plain language

Jeff's instinct was right: any fixed, one-to-one mapping is exactly reversible, so a freshly designed set of 1024-number
codes would also have worked. What was built is the simplest version:

- Each of the 95 characters has one frozen set of **16 numbers** (this is the 16D code; it never changes).
- A 1024-number vector is **64 slots of 16 numbers**. Slot 1 holds the 16 numbers of the first character, slot 2 the second,
  and so on. Unused slots at the end hold a fixed "empty" code.
- So the code for "A" is the same 16 numbers everywhere. What differs from 16D is how many characters fit in one vector:
  16D holds 1, 64D holds 4, 256D holds 16, 512D holds 32, 1024D holds 64. The vector as a whole differs from text to text.
- The "reader" that turns Heart cells into a 1024 vector is a copy-and-place step, and the lowering is the reverse. Tested exact.
- Frozen = the codes. Learned = how the GRU's weights use them. The core still learns to read the 64 slots.
- A separately designed 1024-number code per character (one character per vector) would also be exact but would waste 63/64
  of the space and needs new geometry to be designed and proven. Not recommended; Jeff decides.

## 3. Reading and speaking: guidance on latency

- Reading the field: **64 characters per step (one 1024 vector)** is the recommendation. Latency is the number of
  sequential steps. The old lab measured about 560 characters/second at width 1024 on this GPU (ledger, 2026-09-28), so
  reading a 5,000-character field is about 9 seconds one character at a time; at 64 per step it is about 80 steps, which
  should be well under a second if the per-step cost is similar (ESTIMATE, not measured). Shorter sequences also use less memory.
  Risk: the proven 400/400 recall was one character per step; reading 64 slots at once is untested.
- Speaking: **one character at a time**, each conditioned on the previous one, then pack the result into 64-slot vectors for the
  Heart. Emitting 64 at once from one state makes each character independent of its neighbours and risks misspellings.
- Run the Soul/FFN inner cycles once per heartbeat or per burst of speech, not per spoken letter.
- The core needs: exact ordered characters, an exact lookback at the field (a read head over the mirror), its own spoken
  characters fed back, a region signal, and an "I am done" signal. Build the trainer so both reading modes can be run on
  the same curriculum and compared (accuracy, speed, memory).

## 4. Honest assessment: is the whole architecture worth it?

Jeff asked for candour (he says his engineers always encourage him). This is split into three separate bets.

**Bet A: exact memory, the Heart, provenance (Shared Field, Dormant, masks, Soul lineage). Worth it, on its own.**
Exact, auditable, restartable state with a sole writer is rare and valuable, and it does not depend on how smart the core
is. It is mostly built and tested. Keep it even if the cores disappoint.

**Bet B: small recurrent cores that read and write exact text and eventually reason. Plausible, unproven, and the main risk.**
Evidence so far (all from the lost lab's ledger, not re-run): 400/400 distracted recall (strong for memory); a 1024 GRU reached
perplexity about 3.2 against a 16.1 bigram baseline and spelled real words, but garbled after about 40 unseen characters; the
ledger's own verdict was "next-character prediction, not reasoning". The bottleneck is language competence, which depends on
data and scale far more than on architecture. A GRU of 10-30M parameters trained on tens of megabytes of personal text will
learn that corpus's style and vocabulary; it will not acquire an LLM's world knowledge or reasoning. "Learns that cats are
mammals because it read a book once" does not happen with gradient training at this scale. The design's answer (facts live in
Dormant, retrieved exactly) is the right instinct, but it then needs the core to be good at reading comprehension, which still
needs a lot of varied text.

**Bet C: many cores ticking over a shared field with a rotating consolidator. Not yet earned.**
The lost lab compared elaborations at equal budget (2000 steps, 927 held-out ticks; lower is better):

| Arm | validation perplexity |
|---|---:|
| Plain GRU width 1024 + FFN (baseline) | 2.989 |
| No-FFN GRU widened to the same parameter count | 2.987 |
| Same as baseline, 5 ticks per character | 3.092 |
| 5x compute | 3.116 (undertrained, inconclusive) |

Reading (the ledger's own): the FFN tied with plain width, ticking at equal parameters was worse, and all arms were still
improving at 2000 steps, so this is a ranking at a fixed budget and not a final verdict. It is also not evidence against
multi-core deliberation, which was not what was tested. But there is no measured benefit yet for ticking, the FFN, or
multiple cores, and every one of them multiplies cost (3 cores x inner cycles x reading).

**Semantic edges and episodic memory:** retrieval over exact text with graph links is a proven pattern and a modest, real gain,
if the edges are good. The quality of whatever builds the edges is the risk; start with plain exact retrieval and add edges
only where an A/B shows they help.

**Verdict.** Worth building in measured stages; not worth building all at once on faith. If the goal is a personal, always-on,
auditable, learning system with exact memory and a team of small stateful cores, yes. If the goal is to match a modern LLM's
reasoning from scratch on one 4 GiB GPU, I would not bet on it. The cost of finding out in stages is low and Bet A keeps its value either way.

Highest-leverage options (Jeff's call):
1. **Heterogeneous cores.** The Heart already has an `advisor_input` region. A pretrained model could sit beside the GRU cores
   as one more proposer, with the same Heart rules (proposes, never writes). This conflicts with the v6 "no external teacher"
   doctrine, so it needs Jeff's explicit ruling. It is the fastest route to real language competence inside the same design.
2. **Stronger models make the curriculum, not the core.** Jeff already harvested Codex and Kimi reasoning into 18,546 ticks.
   Cleaning that into the 95 characters and growing it is likely worth more than any architecture change.
3. **Train bigger on Kaggle** (the ledger records 30 h/week on a 16 GB T4/P100) once a small run shows a clear trend.
